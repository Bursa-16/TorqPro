# Material Intelligence, Engineering Formula Validation and a
Readiness-Gated Recommendation Engine (Faz 2.8.8)

- Status: Accepted
- Date: 2026-07-28

## Context

The product owner requested Faz 2.8.8: Material Intelligence,
Engineering Formula Validation, an Engineering Recommendation Engine,
Professional Report integration, and complete TR/EN parity for all of
it, delivered additively with zero regression.

Investigation before any code was written found:

1. `backend/library/material_library.py` is a Phase 1.3 metadata-only
   `BaseLibrary` shell (`status="draft"`, `record_count=0`). It is
   **not** where the real material data lives.
2. Real material data already exists: `backend/library/models.py`
   defines a full `MaterialRecord` (Faz 2.4.2B — material family,
   grade, `rp02_mpa`, `rm_mpa`, `elastic_modulus_mpa`,
   `density_kg_mm3`, `poisson_ratio`, `thermal_expansion_per_k`,
   `confidence_level`-style provenance), populated with 8 real
   records in `backend/library/data/material_library.json` and
   already queryable via `backend.library.population.find_material()`.
   Every one of the 8 records carries `confidence: 3`,
   `validation_status: "reference_only"`, `approval_status: "pending"`
   — uniformly, with no record more "ready" than another.
3. `backend/calculation_engine/formula_registry.py` is an
   intentionally empty engine-level scaffold. The only populated
   formula catalog in the repository is
   `backend.vdi2230_core.trace._CATALOG` (7 entries: `Phi` and `F_S`
   are `APPROVED` per the mandatory corrected model in
   `docs/12_CLAUDE_CONTEXT.md` SS4; the other 5 are `PROVISIONAL`).
   `vdi2230_core` keeps this catalog independent from
   `formula_registry` by design (zero-dependency isolation), and
   nothing currently reads or validates either catalog.
4. No recommendation engine exists anywhere in the repository. The
   nearest precedent, Faz 2.6.4
   (`docs/phases/PHASE_2.6.4_FRICTION_RECOMMENDATION_WARNING_FRAMEWORK.md`),
   deliberately stopped at deterministic warnings + a
   recommendation-*readiness* assessment, and a dedicated test
   asserts that no live friction record reaches
   `engineering_recommendation_ready`. This restraint was intentional,
   not an oversight, and this ADR does not reverse it.
5. `frontend/index.html` carries a known, documented limitation since
   Faz 2.6.8: warning/report prose generated by
   `friction_recommendations.py` / `friction_report.py` /
   `assembly_intelligence*.py` is free-text English only, "deliberately
   left as-is... regardless of `CURRENT_LANG`" because the strings
   have no closed vocabulary to translate against. The same comment
   names the correct fix as "give the backend warnings stable keys
   the frontend can translate" and calls it out of scope for that
   commit.

## Decision

1. **Material Intelligence is built on the existing 8 `MaterialRecord`s,
   not new data.** No new material family, grade, or property value is
   introduced. `backend.calculation_engine.material_intelligence` adds
   requirement-matching (numeric `rp02_mpa`/`rm_mpa`/
   `elastic_modulus_mpa` filters — the fields the record actually
   carries; no temperature/corrosion-class filter was added since no
   live record carries that data) against a stated joint requirement,
   and
   descriptive comparison across the 8 records — the same shape as
   `friction_recommendations`'s comparison capability, generalized to
   quantitative material properties.

2. **The Recommendation Engine keeps the Faz 2.6.4 readiness-gated
   philosophy exactly, per explicit product-owner direction.** A
   `MaterialRecommendationResult` always states a `readiness_level`
   (`data_insufficient` / `comparison_only` /
   `engineering_recommendation_ready` /
   `production_recommendation_ready`), the capabilities available at
   that level, and — when a higher level is *not* reached — the exact
   missing data that would unlock it (approved `approval_status`,
   lot-specific / certified `validation_status`), instead of
   guessing. Given today's data (`reference_only`/`pending`,
   uniformly), the ceiling is `comparison_only`: candidates can be
   ranked by deterministic numeric margin against a stated
   requirement, but every response carries a mandatory disclaimer
   that engineering sign-off is required before production use, and
   no record is asserted `engineering_recommendation_ready` (the
   corresponding test asserts this, mirroring
   `test_faz_2_6_4_...` for friction). This differs from Faz 2.6.4's
   pure non-ranking stance because the underlying data here is
   numeric/quantitative (mechanical properties), not qualitative
   friction ranges — but the *gating discipline itself* (never claim
   a level the data does not support) is unchanged and non-negotiable.

3. **Formula Validation is read-only aggregation, not a new formula
   catalog.** `backend.calculation_engine.formula_validation` calls
   the existing public accessors — `vdi2230_core.trace.all_traces()`
   and `formula_registry.all_formulas()` — and reports counts,
   coverage and per-formula status. It never writes to either
   catalog, never reclassifies an existing formula's
   `validation_status`, and registers no new formula in
   `formula_registry` (that remains explicitly out of scope, matching
   the module's own docstring).

4. **New Faz 2.8.8 warnings/messages carry a stable `code` plus a
   bilingual `{tr, en}` text pair from the moment they are written.**
   This applies only to code introduced in this phase — Faz 2.6.x/
   2.8.6/2.8.7 free-text warnings are not retrofitted (out of scope,
   preserves backward compatibility, no existing behavior changed).
   Every new warning, validation message, recommendation-readiness
   explanation and report section this phase adds is defined as a
   `(code, tr, en)` triple in one place per module, selected by an
   explicit `lang` parameter (`"tr"` default, `"en"` accepted)
   threaded through the engine call, the API endpoint and the report
   collector/renderer — never inferred from `Accept-Language` or
   guessed. Frontend integration follows the existing `t()`
   translation-key convention already used throughout
   `frontend/index.html`.

5. **Reporting follows the established collector/renderer pattern**
   (`friction_report.py`, `strength_class_report.py`,
   `assembly_intelligence_report.py`): a pure `collect_*` function
   calls domain logic exactly once and freezes a dict; a pure
   `render_*` function only formats an already-collected snapshot
   (JSON native, Markdown rendering) — no wall-clock timestamp inside
   the deterministic payload, consistent with every prior phase's
   determinism requirement.

## Consequences

- `backend/library/material_library.py`'s `BaseLibrary` shell metadata
  is left unchanged in this phase (still `status="draft"`,
  `record_count=0`); a later phase may promote the registry entry
  once material records get first-class registry storage instead of
  living only in `population.py`'s JSON-file loader. This ADR does
  not decide that; it is out of scope here (same reasoning as ADR-0009
  point 6 for a comparable case).
- `formula_registry.py` remains empty of concrete entries after this
  phase; only `formula_validation.py`'s read-only report changes.
  Registering real formulas into it is future work requiring its own
  ADR (per `docs/12_CLAUDE_CONTEXT.md` SS4, formula changes require
  documentation + ADR + tests + approval — registering is adjacent to
  a formula change and deserves the same review, not a side effect of
  a reporting phase).
- If/when any `MaterialRecord`'s `approval_status` moves to
  `"approved"` and `validation_status` moves beyond `"reference_only"`
  (e.g. a certified mill-certificate-backed record), the same
  readiness-gate code path automatically re-evaluates to a higher
  level for that record — no code change required, only new,
  approved data (mirrors the Faz 2.6.4 consequence for friction
  records).
- A superseding ADR is required for: registering concrete formulas in
  `formula_registry.py`, promoting any material readiness level above
  `comparison_only`, or retrofitting TR/EN keys onto pre-2.8.8 warning
  strings.
