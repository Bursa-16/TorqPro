# TorqPro AI v3.0.0-rc.1 — Release Notes

**Status:** Released, 2026-08-12.
**Release Commit:** `245e2937863271af220308e1783302f4730f57b8`
**Previous release:** `v3.0.0-beta.2` (Engineering Reasoning Engine)
**Next milestone:** `v3.0.0` — Stable Release

This is a **release-candidate hardening** phase: no new AI capability,
no new engineering engine, and no product feature was added. Its
purpose was to validate, secure, and document the platform ahead of a
stable v3.0.0 release. The deterministic engineering core and the
Torque Recommendation / Engineering Reasoning Engines delivered in
Beta.1/Beta.2 are unchanged in behavior.

Full detail, including individual findings and measurements, is in
`docs/CHANGELOG.md`'s `v3.0.0-rc.1` entry and in `docs/314_Roadmap.md`.
This document summarizes the same work by category.

## Security

- `TORQPRO_ALLOWED_HOSTS` (documented since alpha, never enforced) is
  now applied via Starlette's `TrustedHostMiddleware`.
- Production API documentation exposure closed: `/docs`, `/redoc`, and
  `/openapi.json` are disabled when `TORQPRO_ENV=production`.
- A real cross-user authorization gap was found and fixed:
  `POST /api/calculations` accepted any `project_id` without verifying
  ownership, allowing a calculation to be silently attached to another
  user's project. Fixed by reusing the existing project-ownership
  check already used elsewhere in the codebase; no other authorization
  behavior changed.
- General API rate limiting: centralized, opt-in
  (`TORQPRO_API_RATE_LIMIT`, default off), per-authenticated-session,
  excluding `/api/login` (its own separate limiter, unchanged) and
  `/api/health`.
- Content-Security-Policy on every response (`'unsafe-inline'` for
  script/style, confirmed necessary by inspecting the current
  single-file frontend, not assumed) and Strict-Transport-Security
  (production-only). Pre-existing `X-Content-Type-Options`/
  `X-Frame-Options`/`Referrer-Policy` unchanged.
- Four endpoints that echoed raw exception text to the client now
  return a fixed, safe message while still logging full detail
  server-side; every other similar-looking site in the codebase was
  reviewed and confirmed already safe.
- `pip-audit` added to CI as a dedicated security-scan step; zero
  known vulnerabilities against this repository's actual dependency
  set at release time.

## Performance / Reliability

- A reusable, opt-in performance benchmark suite
  (`tests/performance/`, `TORQPRO_RUN_PERFORMANCE_TESTS=1`) covering
  every critical request path, producing p50/p95/p99 latency and
  throughput. Skipped by default so the normal test suite is
  unaffected.
- SQLite `journal_mode=WAL` and `busy_timeout=5000` enabled on the
  database connection, reducing commit overhead and lock-contention
  risk under concurrent access.
- Concurrency validation: concurrent read/write smoke tests confirm
  no errors, no lost writes, and no data corruption under simultaneous
  requests.
- Critical-path profiling across calculation creation, project
  traceability/release-package, the engineering engines, the AI
  gateway path, and Question Bank retrieval.
- A reproducible local performance baseline for future comparison.

## Known Deferred Items (post-v3.0)

- A strict, nonce/hash-based Content-Security-Policy. The current
  frontend (`frontend/index.html`) is a single-file SPA with one
  inline `<script>` block and roughly 220 inline `style="..."`
  attributes; a stricter CSP would require restructuring it into
  external files first.
- A broad `sync`→`async` route rewrite. No evidence of threadpool
  saturation was found at the concurrency levels exercised in this
  phase's smoke tests.
- A JSON-to-SQLite persistence redesign for the Question Bank and
  washer-resolution stores. Measured read/write cost at current and
  synthetic larger scale remains low; not a present-scale problem.
- A large connection-count or query-shape refactor beyond the
  specific, measured `journal_mode` fix already made.
- Any hard, cross-machine performance regression threshold. This
  phase's benchmark baseline is local and informational, explicitly
  not a checked-in target — sandbox/machine speed is not a reliable
  stand-in for one.
